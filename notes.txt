## What Still Hasn't Changed (The Bad)

### 1. `PLATFORM_DEFS` — Still Hardcoded Python Dicts

```python
Platform.ESP32: {
    "pwm_pins": ["GPIO4", "GPIO13", "GPIO14", ...],
    "i2c_interfaces": [("I2C0", "GPIO21", "GPIO22"), ("I2C1", "GPIO25", "GPIO26")],
    ...
}
```

**Still wrong:**
- **No package variants.** ESP32-WROOM-32 vs ESP32-WROVER vs ESP32-S2 vs ESP32-C3 have different pinouts, PSRAM configurations, and antenna layouts. The agent treats "ESP32" as one thing.
- **No alternate function matrices.** STM32F405 `PA0` can be ADC1_IN0, TIM2_CH1, TIM5_CH1, USART2_CTS. The agent knows PWM but not that TIM2_CH1 and TIM5_CH1 are different timers with different capabilities (32-bit vs 16-bit).
- **No electrical characteristics.** The agent doesn't know that `GPIO34-39` on ESP32 are input-only. It doesn't know that `PA0` on STM32 is 5V-tolerant but `PA1` is not. If you connect a 5V sensor to `PA1`, you fry the ADC.

**What should be done:** External YAML/JSON hardware database with per-package pin matrices, electrical ratings, and errata. Not a Python dict.

### 2. Pin Allocator — Still Greedy, Not a Solver

```python
available = [p for p in pwm_pins if p not in ap["pwm"]]
if available:
    pin = available[0]
```

**Still wrong:**
- **No backtracking.** If allocating `GPIO4` for PWM blocks a later I2C device that needs `GPIO4` for SDA (on ESP32, GPIO4 is I2C_SDA for some configurations), the allocator fails instead of trying `GPIO13`.
- **No cost function.** It picks the first available pin, not the optimal one. On RP2040, `GPIO0` is shared with UART0_RX. If you later add a GPS, you can't because `GPIO0` is already a PWM pin for a servo.
- **No peripheral conflict awareness.** On STM32F405, TIM2_CH1 (PA0) and TIM5_CH1 (PA0) are the same pin. But TIM2 is a general-purpose 32-bit timer, TIM5 is a 32-bit timer with different DMA channels. If you need two independent PWM frequencies, you can't use the same timer channel twice. The agent doesn't track timer instances.

**What should be done:** Constraint satisfaction problem (CSP) with python-constraint, OR-Tools, or a custom backtracking solver. Define constraints: "this pin must support PWM on TIM2", "these two pins must be on different timers", "this pin must be 5V-tolerant."

### 3. Component Templates — Still String `.format()`

```python
code = init_tmpl.format(**ctx)
```

**Still fragile:**
- **No template validation at load time.** A malformed template in a YAML catalog crashes generation at runtime with `KeyError`.
- **No type checking.** If `i2c_address` is passed as string `"0x76"` instead of integer `0x76`, the template renders it literally and the C compiler chokes.
- **No conditional logic.** You can't express "if `i2c_address` is provided, use it; else use default `0x76`" in a `.format()` template. You need Jinja2 or Mako for that.

**What should be done:** Jinja2 templates with schema validation. Load templates, parse them, verify all required variables are declared in the component schema.

### 4. FreeRTOS Integration — Better But Still Shallow

```cpp
static QueueHandle_t sensorQueue = NULL;
static SemaphoreHandle_t i2cMutex = NULL;
```

**Still missing:**
- **Queue sizing.** `xQueueCreate(1, sizeof(SensorData_t))` — one slot. If the actuator task is blocked on a CAN bus write for 5ms, the sensor task overwrites data. You lose samples.
- **No queue sets or event groups.** If you have 3 sensor types (IMU at 1kHz, GPS at 10Hz, barometer at 50Hz), they can't all feed the same queue at different rates.
- **No DMA or interrupt-driven I/O.** The sensor task polls I2C in a loop. Real systems use DMA + interrupt to free the CPU. The generated code will consume 30-40% CPU just waiting for I2C transactions.
- **No tickless idle.** The generated code uses `vTaskDelayUntil` with fixed periods. It never enters low-power modes. Battery-powered devices will drain in hours.

**What should be done:** Generate DMA + interrupt handlers for I2C/SPI/UART. Use notification-based task waking instead of polling. Generate power management code for tickless idle.

### 5. Safety Level — Still Cosmetic

```cpp
#define SAFETY_LEVEL "SIL2"
```

**Still meaningless:**
- **No watchdog implementation.** `setup_watchdog()` and `feed_watchdog()` are commented-out stubs.
- **No safe state definition.** What happens when the watchdog fires? The generated code doesn't define a safe state (all motors off, brakes engaged, valves closed).
- **No redundancy.** SIL2 requires dual-channel or diverse implementation. The agent generates single-threaded code.
- **No traceability.** ISO 26262 requires every line of safety-critical code to trace back to a hazard and risk assessment (HARA). The agent generates code with no requirements IDs.

**What should be done:** If `safety_level != "NONE"`, generate:
  - Independent watchdog timer (IWDG) configuration
  - Safe state handler with hardware interlocks
  - Redundant sensor voting (if 2+ sensors of same type)
  - Requirements trace comments (`// REQ-SAF-001: E-stop response < 50ms`)

### 6. ROS2 Generator — Still Hardcoded Node Graph

```cpp
imu_pub_   = create_publisher<<sensor_msgs::msg::Imu>("/sensors/imu", 10);
range_pub_ = create_publisher<<sensor_msgs::msg::Range>("/sensors/range", 10);
```

**Still wrong:**
- **Publishes IMU and Range regardless of actual components.** If the user specified `gps_neo6m` and `lidar_tfmini`, the sensor node still publishes `sensor_msgs/Imu` and `sensor_msgs/Range` with TODO comments.
- **No dynamic topic generation.** The control node subscribes to `/sensors/imu` even if no IMU is in the component list.
- **No parameter server integration.** PID gains are hardcoded as `static constexpr double`. Real ROS2 nodes load parameters from YAML at runtime.

**What should be done:** Generate the node graph from the actual component list. If no IMU, don't publish `/sensors/imu`. Use `declare_parameter()` and `get_parameter()` for all tunable values.

### 7. PLC Generator — Still One State Machine

```pascal
CASE gSt_State OF
  0: (* IDLE *)
  1: (* STARTING *)
  2: (* RUNNING *)
  3: (* STOPPING *)
  4: (* FAULT *)
```

**Still wrong:**
- **Same 5-state machine for all processes.** A pump doesn't need a "STARTING" state with a 2-second delay. It needs PRIMING → RUNNING → SHUTDOWN. An oven needs PREHEAT → SOAK → COOLING.
- **No sequential function chart (SFC).** IEC 61131-3 has SFC as a native language for sequential control. Structured Text is the wrong paradigm for batch processes.
- **No recipe management.** Industrial ovens, mixers, and reactors run recipes (temperature profiles, timing sequences). The generated code has one fixed setpoint.

**What should be done:** Infer process topology from intent and generate SFC or state machines with domain-specific states. Support recipe/sequence tables.

### 8. Verilog Generator — Better But Still Toy-Level

**The UART fix is genuine** — the 4-state machine with start-bit verification and framing error detection is correct now. But:

- **No CDC (Clock Domain Crossing).** If the FPGA has a 100MHz system clock and a 50MHz ADC interface, the generated code has no synchronizers. Metastability will corrupt data.
- **No timing constraints for generated modules.** The `constraints.xdc` only constrains the top-level clock. It doesn't constrain `set_max_delay` for cross-clock paths.
- **No resource estimation.** The agent doesn't estimate LUT count, BRAM usage, or DSP slices. You could generate a 1024-tap FIR filter that doesn't fit in the target device.
- **No formal verification.** The testbench is simulation-only. Real FPGA workflows use SymbiYosys or Vivado formal verification for protocol compliance.

**What should be done:** Generate CDC synchronizers, resource utilization reports, and formal properties (assertions) for critical interfaces.

### 9. Build System — Still String Templates

```ini
[env:{platform.value.lower()}]
platform = {board_cfg['platform']}
board = {board_cfg['board']}
```

**Still wrong:**
- **No dependency locking.** `lib_deps` lists library names but not versions. Six months later, `Adafruit_BMP280` 2.1.0 might have a breaking API change.
- **No native test integration.** The `[env:native]` section exists but has no actual test files or test runner configuration.
- **No CI/CD generation.** No GitHub Actions, no GitLab CI, no pre-commit hooks.

**What should be done:** Generate `platformio.ini` with version-pinned libraries. Generate `.github/workflows/ci.yml` with build + test + static analysis stages.

### 10. The LLM Problem — Still Unsolved

```python
result = self.llm_provider.generate_json(prompt)
```

**Still dangerous:**
- **No sandboxed compilation.** The LLM generates code, but the agent doesn't attempt to compile it before returning it to the user. A hallucinated API will crash the build.
- **No fallback on LLM failure.** If `generate_json` returns malformed JSON, the agent logs a warning and returns `None`, which falls through to the skeleton stub. But the user doesn't know the LLM failed unless they read logs.
- **No validation of generated templates.** The LLM could generate a template with `{pin}` instead of `{pwm}`, causing `KeyError` at render time.

**What should be done:** Compile-test every LLM-generated template in a sandbox (Docker with cross-compiler) before accepting it. Cache validated templates.

### File: `allocator.py` — Replace Greedy `_allocate_pins`

**Current state:** `available = [p for p in pwm_pins if p not in used]; pin = available[0]`

**Target state:** Constraint solver with backtracking.

```python
from ortools.constraint_solver import routing_enums_pb2
from ortools.constraint_solver import pywrapcp

class PinAllocator:
    def __init__(self, hardware_db: HardwareDB):
        self.db = hardware_db
        self.model = cp_model.CpModel()
        
    def allocate(self, components: List[Component]) -> AllocationResult:
        # Variables: for each component, which pin/peripheral assignment
        # Constraints:
        #   - Each pin used by at most one component (unless bus-shared)
        #   - Each peripheral instance used at most once per function
        #   - Electrical: 5V sensor → 5V-tolerant pin only
        #   - Remap: if TIM2_CH1 on PA0 taken, TIM2_CH1 on PA15 available via remap
        #   - Boot/debug restrictions respected
        
        # Objective: minimize pin spread (keep related pins close), 
        #            minimize peripheral fragmentation,
        #            prefer DMA-capable assignments for high-bandwidth components
        
        solver = cp_model.CpSolver()
        status = solver.Solve(self.model)
        
        if status in (cp_model.OPTIMAL, cp_model.FEASIBLE):
            return self._extract_solution(solver)
        else:
            return AllocationResult(
                status="infeasible",
                conflicts=self._diagnose_conflicts(),
                suggestion="Remove component X or add I2C multiplexer"
            )
```

**Key constraints to encode:**

| Constraint | How |
|------------|-----|
| Pin exclusivity | `AllDifferent` on pin variables, except bus pins |
| Peripheral exclusivity | TIM2 can be used by one PWM component OR one encoder component, not both |
| Electrical compatibility | 5V-tolerant flag as boolean constraint |
| Alternate function remap | If primary pin taken, allow secondary with cost penalty |
| DMA preference | Add soft constraint: high-bandwidth components prefer DMA-capable pins |
| Debug pin protection | Hard constraint: PA13/PA14 reserved unless `allow_debug_sacrifice=True` |
| Boot strapping | ESP32 GPIO0, GPIO2, GPIO5, GPIO12, GPIO15 locked during allocation |

```jinja2
}
```

```cpp
void controlTask(void *pvParameters) {
    SensorData_t sensors;
    ControlOutput_t output;
    
    for (;;) {
        if (xQueueReceive(controlQueue, &sensors, portMAX_DELAY) == pdPASS) {
            compute_control(&sensors, &output);
            xQueueOverwrite(actuatorQueue, &output);
        }
    }
}
```

```python
class ValidationPipeline:
    def __init__(self):
        self.compilers = {
            "esp32": DockerCompiler("espressif/idf:latest"),
            "stm32": DockerCompiler("stm32cubeide:latest"),
            "rp2040": DockerCompiler("raspberrypi/pico-sdk:latest"),
        }
    
    def validate(self, project: GeneratedProject) -> ValidationReport:
        report = ValidationReport()
        
        # 1. Syntax check
        for filename, content in project.files.items():
            if filename.endswith(".cpp"):
                report.syntax = self._run_clang_syntax_check(content)
        
        # 2. Static analysis
        report.misra = self._run_cppcheck_misra(project.files)
        report.clang_tidy = self._run_clang_tidy(project.files)
        
        # 3. Compilation check (no hardware required)
        compiler = self.compilers.get(project.platform)
        if compiler:
            report.compile = compiler.compile(project.files)
        
        # 4. Simulation check (QEMU/Renode)
        if project.rtos == "FreeRTOS":
            report.simulation = self._run_renode_simulation(project.files)
        
        # 5. Pin allocation verification
        report.pinout = self._verify_pinout_against_hardware_db(
            project.pinout, project.platform
        )
        
        return report
```

```python
        # 1. Schema validation
```
